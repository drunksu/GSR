## 2. 实验设计：2×2 析因 + 多顺序模式

### 2.1 两个因子

| 因子 | 水平 | 实现方式（不改被测系统代码） |
|---|---|---|
| **O：执行顺序** | `canonical` 规范序（字典序，= AndroidWorld 默认）<br>`reverse` 反向字典序<br>`shuffle(s)` 随机置换（多 seed）<br>`adversarial(s)` **对抗序**：把同状态域的写任务紧排在读任务之前<br>`seeded_random_global` 跨 Agent 共享的固定随机序 | `order_runner.py` 在 `Suite(dict)` 上重排 key（绕开 `create_suite()` 的 `sorted()`） |
| **R：状态重置** | `official` 官方重置：每任务前后恢复 `task.app_names` 的 App 快照<br>`no_reset` 屏蔽初始化阶段的快照恢复<br>`no_teardown` 屏蔽 `tear_down()`<br>`none` 两者都屏蔽<br>`no_teardown_on_error_only` 只补上"异常路径缺失的 teardown"（E2 的定向修复） | `order_runner.py::_apply_clean_mode()` 运行时 monkey-patch `app_snapshot.restore_snapshot` 与 `TaskEval.tear_down` |

### 2.2 为什么必须有 `adversarial` 顺序（重要）

字典序会把同 App 的任务**连续排在一起**，本身就带污染；而**纯随机置换会把污染稀释**（一个 reader 恰好排在某个 writer 后面的概率 ≈ 1/N）。本仓库实测（33 任务目录）：

| 顺序 | 同簇 writer→reader 紧邻对 |
|---|---|
| `canonical` | 2 对（`SimpleCalendarAddOneEventTomorrow`→`AnyEventsOnDate`、`SimpleCalendarDeleteEvents`→`EventsInTimeRange`） |
| `shuffle(seed=0)` | 1 对 |
| `adversarial` | 3 对（4 个日历读任务中的 3 个都被"安排"了前置写任务） |

**所以"乱序更差"不是自动成立的**：如果只随机置换，很可能测出"乱序甚至更好"（因为字典序更脏）。对抗序给出效应的**上界**，随机序给出**实际部署下的期望**，两者都要报。

合成数据已经复现了这一点（`results/sim/analysis/report.md` 第 2 节，`m3a_gpt4v | none` 一行）：

| 顺序（重置被削弱的条件下） | 套件成功率 |
|---|---|
| `canonical`（字典序） | 0.28 |
| `adversarial`（对抗序） | **0.26** |
| `shuffle`（随机置换） | **0.46** |

字典序把同 App 任务连续排布 → 自带污染；随机置换把它们打散 → 反而**比官方顺序高 18 个百分点**。
这条"反直觉"的结果必须写进论文：它说明**现有评测的默认顺序本身就是一个未被察觉的偏差来源**，同时也警告读者"随便打乱"并不是一个有效的对照条件。

### 2.3 三个对比 + 一个交互项

参照组固定为 **R=official & O=canonical**（"干净基线"）：

| 对比 | 定义 | 回答 |
|---|---|---|
| **C1 污染主效应** | R=弱 & O=规范 vs 干净基线 | 重置不彻底的代价 |
| **C2 顺序主效应** | R=official & O=乱序 vs 干净基线 | **纯顺序**的代价（预期 ≈ 0，即官方重置确实有效） |
| **C3 叠加效应** | R=弱 & O=乱序 vs 干净基线 | 最坏情况的代价 |
| **DiD 交互项** | C3 − C1 − C2（逐任务） | 顺序效应是否**只在污染条件下被放大** |

同时按顺序模式各做一次独立对比（`order:shuffle`、`order:adversarial`、`polluted_order:*`），避免把两种效应量级完全不同的顺序混在一起被稀释。

## 3. 假设（可证伪）

| # | 假设 | 预期观测 | 若不成立说明什么 |
|---|---|---|---|
| **H1** | 状态污染会显著降低后续任务成功率 | C3 的 ΔSR < 0 且 95%CI 不含 0 | 说明污染在 AndroidWorld 级别不构成威胁 → 需转向 MobileBench-OL/A3 等真实在线 App |
| **H2** | 官方 app 快照重置能挡住同 App 污染 | C2 ≈ 0，OD-flaky 率 ≈ 0 | 说明快照机制本身不可靠（更强的结论，值得单独写一节） |
| **H3** | 系统/文件系统类任务（快照覆盖不到）是跨 App 污染源（证据 E1） | `SystemWifi*`/`SystemBrightness*`/`SystemCopyToClipboard`/`Files*` 作为前序时 lift > 1 且 q < 0.05 | 说明污染范围比预期小，或这些任务本身太稳 |
| **H4** | Agent 能力越强，对顺序越不敏感 | OD-flaky 率与检出数随 SR 提升而下降；饱和 Agent（>0.9）≈ 0 | 说明顺序效应与能力无关，是环境属性（同样是可发表的结论） |
| **H5** | 抛异常的任务（跳过 `tear_down`，证据 E2）比成功任务留下更严重的污染 | `no_teardown_on_error_only` 条件能显著降低 ΔSR | 说明异常路径不是主要污染源 |

## 5. 指标定义

设任务 $t$、顺序模式 $o$、重置强度 $r$ 下的成功率为 $SR(t,o,r)$，任务集合 $T$。

| 指标 | 公式 | 含义 |
|---|---|---|
| **ΔSR** | $SR(t,\text{乱序},r) - SR(t,\text{规范},r)$ | 顺序导致的成功率变化（逐任务配对） |
| **OD-flaky 率** | $\lvert\{t: \lvert\Delta SR(t)\rvert \ge \delta,\ q_t < \alpha\}\rvert / \lvert T\rvert$ | 顺序敏感任务占比（默认 δ=0.2, α=0.05，BH-FDR 校正） |
| **CTCI** 跨任务污染指数 | $\mathbb{E}_t[\max_o SR(t,o) - \min_o SR(t,o)]$ | 顺序不确定性带来的成功率全幅（0 = 完全顺序无关） |
| **PASR** 污染感知成功率 | $\mathbb{E}_t[\min_o SR(t,o)]$ | 最坏顺序下的期望成功率 = 评测公平性的**可信下界** |
| **polluter lift** | $P(\text{fail}\mid \text{前序}=P) / P(\text{fail})$ | 污染源排序（配 Fisher 精确检验 + FDR） |
| **DiD 交互项** | $C3 - C1 - C2$ | 顺序与污染的协同放大 |

**报数规则**：ΔSR 一律报"点估计 + 对任务做配对 bootstrap 的 95%CI"；OD-flaky 报"任务名单 + q 值"，不只报一个比例。

## 6. 样本量与统计功效

### 6.1 两种粒度的功效完全不同（这是本实验最容易被低估的一点）

| 目标 | 有效样本量 | 需要多少重复 |
|---|---|---|
| **套件级 ΔSR**（RQ1/RQ3，对任务取平均） | **任务数**（33） | 每 cell **10–12** 次即可：单任务 SR 的 SE≈0.15，33 个任务取平均后 SE≈0.026 → 能稳定检出 ≥0.06 的套件级差异 |
| **单任务 victim 判定**（RQ2） | **每 cell 的 episode 数** | 见下表；ΔSR 越小越贵 |

单任务检出的样本量（`python power_analysis.py --p 0.6` 实测输出，α=0.05, power=0.8）：

| 目标 ΔSR | 每组 episode 数（非配对） | 配对数（McNemar） |
|---|---|---|
| 0.10 | 388 | 312 |
| 0.15 | 173 | 138 |
| 0.20 | 97 | 77 |
| 0.30 | 42 | 33 |
| 0.45 | 17 | 13 |

**策略结论**：
- 主实验每 cell **12 重复** → 能可靠检出 ΔSR ≥ 0.45 的强 victim（对抗序下的典型量级）、以及套件级差异；
- 想把 δ 降到 0.2（覆盖中等强度 victim），需把**对抗序**这一个 cell 的重复数提到 **40+**（成本只增加一个 cell，而不是全部 ×4，这是"只在最强处理组加密"的省算力做法）；
- 论文里写"30+ 次"时务必说明是"每条件每任务"的重复数。

### 6.2 执行预算（公式 + 三档）

$$N_{\text{episodes}} = N_{\text{agent}} \times N_{\text{task}} \times N_{\text{order}} \times N_{\text{reset}} \times N_{\text{repeat}}$$

按 **1.5 分钟/episode**（阶段 0 实测后替换为真实值）估算：

| 档 | 配置 | episodes | 单模拟器 | 4 模拟器并行 | API 费（$0.05/ep） |
|---|---|---|---|---|---|
| **A 试点** | 1 agent × 6 任务 × 2 顺序 × 2 重置 × 10 重复 | 240 | 6 h | 1.5 h | ≈ $12 |
| **B 主实验** | 4 agent × 16 任务 × 3 顺序 × 2 重置 × 12 重复 | 4 608 | 115 h | 29 h | ≈ $230 |
| **B+ 加密** | 在 B 基础上把 `adversarial × none` 提到 40 重复 | 4 608 + 1 344 | 149 h | 37 h | ≈ $300 |
| **C 加强** | 4 agent × 24 任务 × 4 顺序 × 3 重置 × 20 重复 | 23 040 | 576 h | 144 h（≈6 天） | ≈ $1 150 |

`［建议］` 先做 A，用实测的 episode 时长与判定出的信号带重算 B。多模拟器并行时**每个模拟器必须独立 AVD 实例 + 独立 console port**（`--console-port 5554/5556/5558`）。

## 7. 统计方法

1. **逐任务配对检验**：Fisher 精确检验（结果 0/1；复合任务按 0.5 阈值二值化，均值仍用原始分数）+ Benjamini–Hochberg FDR（按 agent × 对比分组校正）。
2. **套件级置信区间**：对**任务**做 2 000 次配对 bootstrap 取 2.5/97.5 百分位（`analyze_order_effects.py` 已实现，纯标准库）。
3. **配对设计（可选增强）**：同一 repeat 下标下用 McNemar 检验（规范序成功/乱序失败 vs 反之），对 API 抖动更鲁棒。
4. **多 Agent 汇总（论文级）**：建议再加一个混合效应 logistic 回归
   `success ~ order * reset + (1|task) + (1|agent)`，把任务与 Agent 作为随机效应，用 DiD 作为交互项的正式估计。
5. **多重比较**：跨 agent、跨顺序模式、跨任务的对比很多 → 报告 FDR 校正后的 q 值，并明确"探索性 vs 确证性"分析的分界。

## 9. 管道自检结果（已跑通，可复现）

用 `make_sim_data.py` 生成 **22 176 条 episode**（4 agent × 2 重置 × 7 顺序 × 12 重复 × 33 任务），注入机制为：
"同簇 writer 前序 → reader 成功率 −0.45；系统/文件系统前序 → 全局限 −0.12；`official` 条件无污染；另有 ±0.03 无关噪声"。
然后用 `analyze_order_effects.py` 盲跑分析（不看 ground truth 调参），最后与 ground truth 对比。

**逐 agent 结果**（`order:shuffle` 三个 seed 合并统计）：

| Agent | C2 顺序主效应（official 下） | polluted + adversarial | OD-flaky 率 | DiD 交互项 |
|---|---|---|---|---|
| `t3a_gpt4` | ΔSR = −0.009 [−0.048, +0.034]，0 victim | **ΔSR = −0.302** | 39.4%（13/33） | **+0.074** [0.004, 0.149] |
| `m3a_gpt4v` | ΔSR = +0.022 [−0.039, +0.079]，0 victim | **ΔSR = −0.250** | 45.5%（15/33） | +0.060 [−0.027, 0.145] |
| `seeact` | ΔSR = +0.003 [−0.041, +0.048]，0 victim | **ΔSR = −0.193** | 39.4%（13/33） | **+0.102** [0.044, 0.160] |
| `minitap_multi` | ΔSR = −0.020 [−0.044, +0.005]，0 victim | **ΔSR = −0.298** | 42.4%（14/33） | **+0.116** [0.048, 0.185] |

| 观测 | 结果 | 说明 |
|---|---|---|
| **C2 顺序主效应（official 条件下）** | 4 个 agent 的 ΔSR 全在 ±0.022 内、CI 全部含 0、**victim 数全为 0** | 与 **H2** 一致：重置有效 → 顺序无害 |
| **`polluted_order:adversarial`** | ΔSR **−0.19 ~ −0.30**，OD-flaky **39%–46%**，每 agent 13–15 个 victim | **H1** 成立：重置被削弱后顺序造成的损失可达 30 个百分点 |
| **DiD 交互项** | +0.060 ~ +0.116（4 个中 3 个 CI 不含 0） | 顺序效应**确实只在污染条件下被放大** |
| **`order:shuffle`（官方重置下）** | ΔSR ≈ 0 | 纯顺序本身无效应，效应来自"顺序 × 污染" |
| **自检 precision / recall** | **0.95 / 0.63**（TP=19, FP=1, FN=11） | 19 个真 victim 被检出，仅 1 个"暴露次数略少但观测上仍显著"的边界任务被判为 FP |
| **polluter top-k precision** | 0.54 | 排在榜首的确实都是真污染源，但**序不稳定** → 要稳定排序需把重复数提到 40+（对应 §6.1） |

**读法**：这正是论文期望的结果形态——**官方重置下顺序无害（H2），重置被削弱后"顺序 + 污染"叠加造成约 30 个百分点损失（H1），且两者存在显著交互（DiD > 0）**；而中等强度受害者在 12 重复下会被漏检，给出了后续加密重复数的明确依据。

**一键复现**：`python selftest.py`（13 项检查全绿，见 `README.md`）。

## 11. 效度威胁与缓解

| 威胁 | 说明 | 缓解 |
|---|---|---|
| **API 非确定性** | 同一 agent 两次跑结果不同，会把噪声算成顺序效应 | `temperature=0`；每 cell ≥10 重复；配对设计（McNemar）+ FDR；负对照平台 |
| **天花板/地板效应** | 顶端 agent 全对、弱 agent 全错 → 测不出 OD | 信号带筛选（0.2 ≤ SR ≤ 0.8），分档报（H4） |
| **字典序自带污染** | "规范序"不是干净序 | 参照组用 **official+canonical** 而非 weak+canonical；同时报 canonical/shuffle/adversarial 三种顺序的独立结果 |
| **模拟器与真机差距** | AndroidWorld 是模拟器 + 开源 App，生态效度有限 | 阶段 3 用 MobileBench-OL 真机 + 真实在线 App 复核 |
| **快照掩盖现象** | 官方重置太有效，主效应可能不显著 | 这本身是结论（H2）；把 `none` 条件作为"现实部署"的代理，并在 MobileBench-OL 上验证 |
| **`tear_down` 异常路径（E2）** | 失败任务跳过清理，效应与"agent 能力"耦合 | 单设 `no_teardown_on_error_only` 条件做定向检验（H5） |
| **多模拟器并行差异** | 不同 AVD 实例/主机差异引入系统偏差 | 每个 (agent, 条件) 组合内部保持同一模拟器；顺序模式在模拟器间轮换（Latin square） |
| **任务参数随机性** | 参数不同导致难度不同 | 固定 `--task_random_seed`；同一 task 的所有条件下用相同参数（`use_identical_params`） |
