# 方法说明

## 第一部分　总体设计

### 1. 要解决的问题

任务在手机上连续执行，前一个任务留下的状态会影响后面的任务：夜间模式没关、好友申请还挂着、搜索框留了记录。动机实验测过，中间不清理时，成功率掉 12 到 15 个百分点。

官方自带的清理方式是人工写一句清理指令，让同一个 agent 执行，有三个问题：

- 310 个任务里只有 65 个写了清理指令，其余没有；
- 清理完不检查，不知道到底干净没有；
- 清理失败和成功在记录里没有区别。

### 2. 方法分三步

1. **推断**：读任务描述和执行轨迹，输出一份污染清单，记录这次执行留下了什么。
2. **生成**：根据污染清单写一个恢复任务，内容包括恢复目标、执行前检查、执行后应该看到的结果。
3. **执行**：让 GUI agent 按恢复任务操作手机，操作前后都检查。

### 3. 基本原则

恢复操作本身也是在操作手机，恢复错了就等于制造新的污染，比如删错好友、再发一条消息。所以：

- 恢复目标可以让模型自由写；
- 执行必须受控：动手前先看当前状态，已经干净就什么都不做；动手后由另一个模型检查结果，不让执行者自己给自己打分；
- 遇到不确定、不可逆、模型没把握的情况，停下来等人处理，不靠猜。

### 4. 输入数据

每条轨迹包含：任务描述、每一步的 Thought（执行 agent 的想法）和 Action（点击坐标、输入文字原文），真机上还有逐步截图。

官方的 success 判定不能用来判断有没有残留。实际见过三种情况：任务失败但搜索词已经留下（qq_1）、任务失败但夜间模式确实打开了（baidubrowser_14）、任务判成功但其实只是浏览。有没有残留只能看轨迹本身。

### 5. 生成恢复任务（Recovery Task）

污染清单里每条需要处理的变更生成一个恢复任务，主要内容：

- **recovery_goal**：恢复目标，可以自由写，但只能用污染清单里有轨迹证据的人名、号码、设置名，不许编；
- **precondition**：执行前检查当前是什么状态。如果已经干净，直接算成功，不做任何操作（保证连跑多次结果一样）；
- **expected_end_state**：恢复后应该看到什么。执行完由独立的 VLM 判断；
- **risk_level**：风险等级。高风险操作（删好友、退群、发消息、删任务开始前就存在的内容）只生成、不自动执行，直接交给人工。

### 6. 执行和验证

执行器固定用 qwen3-vl-plus，流程：

```
PRECHECK（先检查当前状态）
  ├─ 已经干净   → 记为 no-op 成功，0 个动作
  └─ 有残留     → 执行
                   ├─ 出错或超过步数上限 → 挂起，等人工
                   └─ 执行完 → VERIFY，独立 VLM 判断结果
                                ├─ 符合预期   → 恢复完成
                                └─ 不符合     → 最多重试 1 次，再不符合就挂起
```

另外两条：

- 恢复过程自己的轨迹会再跑一遍推断，检查恢复动作有没有留下新的副作用，比如恢复时又输入了搜索词；
- 每一步的状态转移和截图都保存下来，人工干预率作为正式指标。

### 7. 评测安排

- **阶段 A（已完成）**：不用手机，离线评测推断质量。
- **阶段 B**：小批量真机，测前置检查正确率、恢复成功率、连跑两次的幂等率、恢复动作副作用率、挂起率。
- **阶段 C**：在 s3 的 4 个任务上对比三种条件：不恢复 / 本方法 / 官方 cleaner，沿用动机实验的 ΔSR、CTCI、PASR 指标。

### 8. 以后的 RL 路线

闭环跑通以后，执行器可以换成可训练模型。奖励直接从状态机读数：验证通过 +1、没有副作用 +0.5、查出副作用 −1、挂起 −0.5、每步 −0.01，不需要人工标注。阶段 B、C 攒下的数据可以直接做训练语料，训练放在模拟器上并行跑，真机只做最终评测。中期之前只做提示式，不做训练。

## 第二部分　推断模块

### 1. 输入和输出

输入是任务描述加上每步的 Thought 和 Action，模型用 qwen3-vl-plus，temperature=0。链式批量跑的时候，还会带上前一个任务的污染清单。

输出是一个 JSON 污染清单（schema 版本 contamination-list/v0.1）。每条变更记录：类型、App、实体（名字和硬标识，比如 QQ 号）、方向、存在哪里（服务器 / 账号 / 本机 / 当前会话）、状态（完成 / 待处理 / 做了但不确定 / 没做）、可逆性、证据步号、轨迹原文引文、置信度、归因（本任务造成 / 前序遗留 / 任务开始前就有）。

### 2. 变更类型

| 类型 | 含义 | 能不能自动恢复 |
|---|---|---|
| settings_toggle | 夜间模式、长辈模式等开关 | 可以，拨回去 |
| relationship_request | 好友申请 | 待审批可以取消；已通过要删好友，走人工 |
| membership_change | 加群、退群 | 影响群和对方，走人工 |
| content_lifecycle | 新建或删除笔记、帖子、日程 | 自己刚建的可以删；删掉的旧内容无法还原，走人工 |
| message_send | 发消息 | 不可逆，走人工 |
| social_reaction | 关注、点赞、收藏 | 可以，再点一下取消 |
| session_state | 播放、页面栈等 | 按 Home 就没了，不算残留 |
| search_history | 搜索框输入记录 | 可以，逐条删 |
| login_session | 登录态 | 视情况 |
| other | 兜底类型 | 必须低置信并引用原文 |

置信度低于 0.7 的条目不允许自动恢复，直接进人工门控。

### 3. 处理流程

模型输出的内容不是直接采用，后面有一串检查：

1. **枚举和字段校验**：类型、方向等值只能从固定列表里选，不许自造；顶层搜索词和搜索历史条目必须对得上；carried_over 必须写清来源任务。
2. **接地检查**：把污染清单拿回轨迹原文里逐条核对：
   - QQ 号这类硬标识必须在轨迹里逐字出现；
   - 实体名字必须能在轨迹里找到（字组覆盖率阈值 0.80）；设置项要写选项名（"关怀模式"），不能写容器名（"通用设置"）；
   - 引文必须是轨迹原文（字组覆盖率阈值 0.75），不许改写或把不相邻的句子拼起来；
   - 证据步号不能超出轨迹长度；
   - 搜索词必须对应搜索框里的输入。申请表问答题框里打的字不算搜索词。
3. 检查不通过，把具体错误发回模型修一次；再不通过直接报错，不写污染清单。
4. 有确定性判据的错误由代码直接处理。比如登记的搜索词在轨迹里找不到对应的搜索框输入，代码直接剔除这条，并在 `_warnings` 里留痕。

纯浏览、导航类任务的正确输出就是空污染清单，乱登记在评测里算误报。是否需要恢复不单独标注：**清单非空就需要恢复，空清单就不需要**。

### 4. 链式任务怎么利用前序轨迹

批量执行时按 episodes.jsonl 的顺序推断，每个任务除了自己的轨迹，还能看到前一个任务污染清单里没清掉的残留。

早期版本让模型自己把前序残留抄进新污染清单，实测有三个问题：

- 当前轨迹里看不到的残留（比如更早任务留下的搜索词），模型直接漏掉；
- Thought 里出现旧词，模型会当成这次新输入的；
- temperature=0 下这些错误发回重改也改不动。

现在的做法是**模型只判断当前任务，污染清单合并由代码完成**：

- 前序污染清单里还没清掉的残留，代码原样搬到新污染清单，标成 carried_over。本任务零输入也不丢；
- 前序已有、本任务没有重新输入的搜索词，自动从 this_task 改判成 carried_over；
- 每条 carried_over 记录最早来源任务，比如 DND 一直追溯到链首的 qq_1；
- 门控跟着残留走：前序的不可逆残留（比如已经发出的消息）在后续每个任务的污染清单里都保持挂起，下游任务不能当它不存在；
- 某条任务推断失败，后面的任务就不传前序了，宁可不知道也不假装知道。

实测两条链（q2 的 8 个任务、s3 的 4 个任务）：链尾残留一条没丢，两个人工门控一直传到最后，中间没有输入的任务没有被误判成需要恢复。

### 5. 评测结果

金标集 41 个 case、76 条变更，人工对照轨迹原文逐条标注，链式 case 把前序残留的完整集合都列出来了，其中 7 个是"应该为空污染清单"的反例。

2026-10-10 的结果：

| 指标 | 结果 |
|---|---|
| micro 精确率 | 0.987 |
| micro 召回率 | 0.974 |
| micro F1 | 0.980 |
| 状态判定准确率 | 1.000 |
| 搜索词召回 | 1.000 |
| 空污染清单特异性 | 1.000 |
| 门控判定准确率 | 0.900 |
| 接地硬违规 | 0 条 |

三个没解决的真实失败，没有靠改金标或放宽检查盖过去：

1. **rimet_6**：钉钉加好友，点了发送之后掉进群聊，重新搜索显示"该用户不存在"，申请到底发没发、有没有发给错的人，都不确定。模型却以 0.95 置信度报完成，门控没挂上。这是门控准确率唯一的失分点。
2. **rimet_16**：状态确实改成功了（有"保存成功"），但模型把实体名写成容器名"我的状态"，应该写选项名"下班了"。
3. **pinduoduo_27**：任务是开长辈模式，agent 一直没找到，最后在字体大小页点了一下，没有任何生效反馈。模型给了空污染清单直接跳过，正确做法是标成"做了但不确定"并挂起。

下一步改进方向：终局 Thought 出现"不存在 / 没找到 / 无法"这类否定时，强制把同一实体的完成状态降级重判；进一步区分设置项选项名和容器名；没有生效反馈的点击默认按不确定处理。
